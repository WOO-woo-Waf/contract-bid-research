# 合同审核与智能投标落地路线

形成日期：2026-08-04

## 背景与目标

路线以“先建立证据和评测，再做生成体验”为原则。已有 MinerU 负责解析；新工作聚焦领域任务、证据链、规则库、金标集和人工工作流。

## 非目标

- 不新建解析器、OCR 服务或重复队列。
- 不在没有金标集前做大规模微调。
- 不同时启动合同和投标全部功能的产品化。
- 不把公众号功能清单当需求基线。

## Phase 0：两周内形成可测底座

### 工作项

1. 固定 MinerU Canonical JSON v1 和 SourceAnchor v1，确认现有适配实现状态。
2. 在 OpenContracts 做一个 MinerU parser adapter spike，导入一份 PDF 和一份 DOCX，验证原文回跳。
3. 定义合同 `RiskFinding`、投标 `Requirement`、全局事实和生成主张 JSON Schema。
4. 建立脱敏流程和数据分级；用 Presidio 扩展中文/企业 recognizer。
5. 选定首批 2 类合同、2 类招标文件，制作小规模双人标注集。
6. 跑规则/BM25 基线，接入本仓公共评估函数。

### 出口门禁

- 解析结果可稳定回到页/段/表格位置。
- 每个标签有定义、正反例和冲突处理规则。
- 数据集按文档隔离，无模板泄漏。
- 测试数据完成匿名化和授权登记。

## Phase 1A：合同审核 MVP（若合同优先）

### 范围

- 主体/日期/金额/期限/关键条款抽取。
- 20～40 条版本化 playbook 规则。
- 风险、缺失、冲突和证据定位。
- 人工确认、忽略、改级别、写意见和导出报告。
- 最小修订建议，不自动覆盖合同。

### 推荐实现

- OpenContracts 负责语料、标注、权限、抽取任务和审阅界面。
- 规则引擎处理确定性事实；混合检索 + NLI/LLM 处理语义规则。
- 每次审核保存 parser/model/prompt/rule 版本和证据快照。

### 门禁

- 金标小集重大风险无漏检；未知数据不宣传“零遗漏”。
- 所有结论有证据或明确标记不可判定。
- 法务审核者能在原文、风险和建议之间来回定位。

## Phase 1B：投标合规 MVP（若投标优先）

### 范围

- 标段、资格、评分、废标、技术/商务要求和时间节点矩阵。
- 项目全局事实、企业材料有效期和可披露等级。
- 需求到章节/材料/责任人的合规矩阵。
- 废标检查与矛盾检查，暂不追求十万字全自动生成。
- 导出合规矩阵和待办清单。

### 门禁

- 固定样例废标项和必选项覆盖 100%。
- 每项要求能回到招标原文，响应能回到投标章节/材料。
- 任何缺失资质、案例或参数以占位/待办呈现，不允许虚构。

## Phase 2：有依据的生成与修订

1. 按评分权重和需求覆盖生成目录。
2. 建立章节材料包，逐节生成并输出 claim-evidence 映射。
3. 增加全局事实、术语、参数、承诺和跨章节一致性检查。
4. 引入人工接受率和无依据主张率，只有错误分析证明收益后才微调。
5. 易标代码复用取决于 AGPL 决策；未决前只作黑盒/源码研究参考。

## Phase 3：编辑协作与全生命周期

1. 用真实模板验证 VerveDocs 或其他 Word 编辑方案。
2. 增加批注、修订、版本、审批、电子签章/归档连接器。
3. 协作认证必须接企业身份和文档 ACL，不能使用 VerveDocs 当前自报 userId token。
4. 合同履约提醒、投标任务进度和归档是后续业务模块，不混入审查算法内核。

## 详细变更清单

| 模块 | 新增 | 复用/保持 |
|---|---|---|
| Parser adapter | MinerU Canonical JSON → 领域块/SourceAnchor | 保持现有 MinerU 服务和队列 |
| Domain schemas | Contract/Requirement/Risk/Facts/Claims | 不改变解析内部 JSON |
| Rule service | 规则 DSL、版本、适用范围、严重度、测试 | 不让 Prompt 充当唯一规则库 |
| Retrieval | BM25/dense/rerank/邻域/权限过滤 | 可复用 OpenContracts pgvector/语料 |
| Evaluation | 金标、基线、回归、错误分类 | 使用本仓 task taxonomy/metrics |
| Review UI | 证据定位、状态、审批、报告 | 优先扩展 OpenContracts |
| Bid workflow | 合规矩阵、目录、分节、检查 | 参考易标任务拆分 |
| Editor | DOCX 编辑/导出回归 | 评估 VerveDocs，不原样使用协作鉴权 |

## 必要重构说明

- MinerU 适配必须以 Canonical JSON 为稳定边界，不能让领域代码直接读取 `middle.json` 的临时结构。
- LLM 调用统一经过一个可审计客户端，显式模型、超时、token 上限、温度和用途；领域代码不得散落 Base URL/API Key。
- 规则、Prompt、模型和法规知识分别版本化，避免一次模型升级同时改变全部行为。
- AGPL 与 MIT 代码在仓库、进程和接口边界上清晰隔离，最终边界由法务决定。

## 风险与回滚

- 如果 OpenContracts 过重：保留其数据模型/标注思路，先实现轻量领域 API；不要因此退回无证据的一次性 Prompt。
- 如果 VerveDocs DOCX 保真不达标：首期仍用模板化导出 + Office 本地编辑，不阻塞审核 MVP。
- 如果 LLM 语义规则误报高：降级为检索候选 + 人工判断，确定性规则继续服务。
- 如果 MinerU 某类文档质量不足：按现有设计升级 effort/route，Docling 仅作对照，不拆第二套生产栈。

## 验证计划

- 单元：schema、规则、指标、数字/日期/主体归一化。
- 数据：双人一致性、专家仲裁、文档级切分、脱敏抽检。
- 算法：规则/BM25/dense/LLM 同集对照和分层指标。
- 集成：MinerU → SourceAnchor → 风险/需求 → 原文回跳。
- 编辑：复杂 DOCX 视觉和结构回归，Windows/Office 实机打开。
- 安全：租户隔离、出站白名单、遥测关闭、日志脱敏、删除和审计。

## 需要业务负责人确认

1. 合同审核和投标合规哪个先做 MVP。
2. 首批文档类型、行业、审查立场和业务负责人。
3. 是否允许 AGPL 独立组件，或必须全链路宽松许可证/自研。
4. 生产模型必须完全本地，还是允许经审批的企业模型网关。
5. 首期是否要求在线多人 Word 协作。
