# 合同审核与智能投标任务及算法基线

形成日期：2026-08-04

## 背景与目标

两个领域都不能被简化为“一次长 Prompt”。本设计把任务拆成可标注、可测量、可追溯的小任务，并定义从规则基线到模型增强的演进顺序。机器可读版见 `research/task_taxonomy.yaml`。

## 非目标

- 不在本阶段训练生产模型。
- 不把模型置信度当作法律风险等级。
- 不允许无来源的法规引用、合同事实或投标承诺进入最终交付。
- 不用单一总体准确率掩盖关键废标项或重大风险漏检。

## 通用数据合同

领域层至少稳定维护五类对象：

| 对象 | 关键字段 | 约束 |
|---|---|---|
| `SourceAnchor` | document/version/page/bbox/block/span/native_anchor | 必须能回到固定版本原文；解析器升级不改业务 ID |
| `CanonicalFact` | key/value/unit/date/party/evidence/conflicts | 同一事实多来源冲突必须显式保留 |
| `Requirement` | id/type/mandatory/score/rejection/deadline/evidence | 任何废标结论至少一个原文锚点 |
| `RiskFinding` | rule/severity/affected_party/rationale/evidence/suggestion/status | 风险等级来自规则/playbook，不由模型自由决定 |
| `GeneratedClaim` | claim/text/evidence/fact_ids/commitment_level/reviewer | 无证据事实应拒绝、降级为占位或要求人工输入 |

所有对象携带 `parser_version`、`model_id`、`prompt_or_rule_version`、`created_at` 和人工审核状态，以便复现和审计。

## 合同审核任务链

### 1. 合同识别与结构化

输入 Canonical Document JSON，输出合同类型、主体、角色、日期、金额、定义、条款层级、附件与交叉引用。

基线算法：

- 样式/编号/版面规则分段；正则和词典抽取日期、金额、统一社会信用代码、期限。
- LLM 只补充复杂字段，使用 JSON Schema 严格约束并逐字段附来源。
- 表格和正文分别抽取后做实体归一化，不把“甲方/采购人/招标人”直接视为同一实体，必须由证据合并。

### 2. 条款分类与缺失检测

先按合同类型加载应有条款清单，再做多标签分类和缺失判断。缺失不是“没有检索到”即成立，应检查同义标题、正文散落表达、附件和交叉引用。

算法路线：词典/BM25 召回 → dense embedding 召回 → cross-encoder/LLM 重排 → NLI 判断“存在/冲突/未提及” → 人工复核。ContractNLI 的 entailment/contradiction/not-mentioned 任务形式可直接借鉴，但标签需中文化和业务化。

### 3. 风险与 playbook 符合性

规则分三层：

1. 确定性规则：主体资质、金额/税率/期限、管辖冲突、仲裁与诉讼并列、禁止词、必备字段。
2. 语义规则：责任不对等、单方变更、无限责任、知识产权归属、保密例外、自动续期等。
3. 法规/政策规则：带生效时间、适用地域、行业和来源版本的知识条目。

每条规则输出 `pass/fail/uncertain/not_applicable`，模型不得把 `uncertain` 静默变成 `pass`。重大风险优先召回，低风险优先控制误报。

### 4. 跨条款一致性

建立事实表和引用图后检查：名称、金额、日期、期限、交付/验收、发票/付款、违约责任、争议解决、附件优先级。数值和日期走确定性比较；语义冲突使用 NLI/LLM，但必须返回冲突的两个锚点。

### 5. 修订与报告

修订建议采用“最小改动”策略：原文、建议文本、变更类型、理由、受益/受损方、残余风险、证据和审批人。禁止直接覆盖原合同；输出 redline 或结构化 patch，并要求唯一定位和人工接受。

## 智能投标任务链

### 1. 招标需求矩阵

先抽取标段，再按采购范围、资格、商务、技术、评分、废标、格式/签章、时间节点分类。一个要求可能横跨正文、评分表和附件，必须保留多来源锚点和冲突。

### 2. 全局事实与企业素材

项目名、编号、标段、工期、地点、质保、人员、设备、承诺和资质形成 Canonical Facts。企业知识库素材必须带有效期、适用行业、所有者和可披露等级；模型不得虚构资质、案例、人员或性能指标。

### 3. 合规矩阵与目录规划

每个 `Requirement` 映射到响应章节、证据材料、责任人和状态。目录生成以需求覆盖为硬约束，以评分权重分配篇幅为软目标；先保证废标/必选项，再优化得分和篇幅。

可用目标函数示意：

```text
maximize  Σ(score_weight × response_quality)
          - unsupported_claim_penalty
          - inconsistency_penalty
subject to rejection_requirement_coverage = 100%
           mandatory_requirement_coverage = 100%
           all factual claims have evidence or explicit placeholders
```

### 4. 有依据的分节生成

生成上下文只包含本节需求、全局事实、获准素材、相邻章节摘要和禁用承诺。正文中的可核验主张写入 `GeneratedClaim`，关联事实和证据。长文并发生成后必须做全局事实校验、术语校验、承诺校验和章节交叉检查。

### 5. 废标、查重和导出

- 废标检查采用规则高召回 + 模型解释，扫描件不可见时标记“证据不可判定”，不能直接判缺失。
- 查重区分合法模板复用、企业标准表述和可疑高度重合；相似度不是侵权结论。
- DOCX 验收包括标题编号、目录、页眉页脚、表格、图片、分页、字体和模板域，不以纯文本正确代替排版正确。

## 检索与长文档策略

推荐混合检索：

1. 结构过滤：合同类型、条款类型、文档版本、标段、密级、有效期。
2. BM25：编号、专有名词、法规条号、参数等精确召回。
3. Dense retrieval：同义表达和语义召回。
4. Reranker：针对具体任务重排。
5. 邻域扩展：返回命中条款的标题、前后条款、定义和引用附件。
6. Citation check：答案每个结论必须由返回片段蕴含，不能只因“检索到了相关内容”就算有依据。

长文处理按文档结构分层，不按固定 token 生切：文档 → 章节 → 条款/表格 → span。Map 阶段提取局部候选，Reduce 阶段做去重、冲突和缺失检查，最后用全文索引做反证搜索。

## 公开数据集与用途

| 数据 | 固定快照事实 | 可用于 | 不足 |
|---|---|---|---|
| CUAD | 510 份合同、41 类问题、20,910 个问答、13,823 个答案 | 条款抽取、needle-in-haystack、span 指标 | 英文商业合同；根许可证不清晰，生产训练前需复核 |
| ContractNLI | 607 份 NDA、17 个固定假设，标签为蕴含/矛盾/未提及并带证据 span | 条款符合性、矛盾和证据识别 | 英文 NDA，领域和标签覆盖窄 |
| 自有中文金标集 | 尚待建设 | 真实验收和回归 | 必须匿名化、按文档划分、双人标注和专家仲裁 |

训练/评测必须按完整文档切分，不能让同一合同模板的不同版本跨 train/test；否则指标会被模板泄漏夸大。

## 评测协议

### 核心指标

- 抽取：字段 Exact Match、span precision/recall/F1、表格 cell accuracy。
- 风险：按严重级别分层的 precision/recall/F1，重大风险单列 recall。
- 需求：普通/评分/必选/废标项分层覆盖率，加权覆盖率。
- 证据：evidence precision/recall、grounded claim rate、错误引用率。
- 生成：事实一致率、无依据主张率、人工接受率、修改距离。
- 导出：结构/视觉回归、可编辑性、Office 打开成功率。
- 系统：页数/字数分桶延迟、成本、失败恢复、人工耗时节省。

建议把 `重大风险漏检=0` 和 `废标项漏检=0` 作为小规模验收集上的硬门禁，但不能把它包装成对未知生产数据的“零遗漏”承诺。

### 最小基线

第一版不要先微调大模型。按以下顺序建立可比较基线：

1. 正则/词典/编号规则。
2. BM25 + 人工规则。
3. Dense retrieval + reranker。
4. 结构化 LLM 抽取（固定模型、温度 0、JSON Schema）。
5. NLI/LLM 语义判定。
6. 只有错误分析证明收益后再做 LoRA/微调。

仓库的 `src/contract_bid_research/evaluation.py` 已提供最小风险检测 P/R/F1、加权需求覆盖率和证据落地率函数，作为后续实验公共口径。

## 风险控制

- 模型失败、证据不足或解析质量差时必须 abstain，不得给出确定结论。
- 关键金额、日期、项目编号、主体、工期和性能参数由确定性校验兜底。
- 法规库和企业 playbook 独立版本化；模型参数升级不能隐式改变规则。
- 输出页面显示来源、规则、模型和审核状态；保留人工改动轨迹。
- 测试数据不含真实客户秘密；生产数据按租户隔离并设置留存/删除策略。

## 验证计划

1. 用 10 份数字 PDF、10 份扫描 PDF、10 份 DOCX 验证 Canonical Anchor 回跳。
2. 建立至少两类中文合同和两类招标文件的双人标注小集。
3. 跑规则、BM25、dense、LLM 四档基线并做同一错误分类表。
4. 对每次模型/Prompt/规则变更执行固定回归集。
5. 把重大风险、废标项、无依据主张和排版破坏设为发布门禁。
